## 1. The bounty counted twice in `winnings` (CODE FIXED 16 Oct — data pending)

`game-state.js` ~line 1084, in `finalize()`:

```js
winnings: win + bnty,
bounty:   bnty,
```

The bounty is stored inside `winnings` **and** in its own `bounty` field, while
`pot` already has the bounty deducted off the top
(`pot = gross - kitty - bounty`). So whenever a bounty is claimed:

    sum(winnings) == pot + bounty

### Observed in live data

| Event | pot | sum(winnings) | delta |
|-------|------|------|-------|
| 1 — 2026-09-03 | $550 | $550 | ✓ (no bounty in play) |
| 2 — 2026-09-15 | $700 | $720 | +$20 |
| 3 — 2026-10-01 | $750 | $770 | +$20 |

**The cash at the table was correct both nights.** Jacob confirmed for Event 3:
Phil T handed him $20 on the knockout, and he collected $60 from the pot when he
busted in 5th. The record says `winnings: 80` — the $20 folded in on top of the
$20 already in `bounty`.

### The test agrees with the bug

`dress-rehearsal.js` ~line 365:

```js
if (handed !== game.pot + (game.bounty||0)) note(night,'money does not balance')
```

It *expects* the inflated sum. Correct data would make this check fail. That is
why nothing ever flagged it — code and test agree, and only the human-facing
results page disagrees ("Paid out $750" printed beside a column summing $770).

### Second-order damage: phantom cashes

`data.js` ~line 882:

```js
if (r.itm || (r.winnings || 0) > 0) p.cashes += 1;
```

Event 2: Sprayberry took the bounty off Tod but busted 5th when only four
places paid — `itm: false`, `winnings: 20` (all bounty). He is credited with a
cash he never made.

### Fix — CODE FIRST, THEN DATA. Order matters.

Season aggregation (`data.js` ~879) sums `winnings` and **never looks at
`bounty`**. So zeroing the data cells first would delete $40 of real bounty
money from the season record. Sequence:

1. `game-state.js`: `winnings: win` (drop `+ bnty`) — `winnings` means pool money.
2. `data.js` ~879: add bounty into the season money total, so bounties still count.
3. `data.js` ~882: key `cashes` off `itm` alone, not `winnings > 0`.
4. `dress-rehearsal.js` ~365: expect `handed !== game.pot`.
5. Full Playwright suite (24 browser files + 3 engine files).
6. THEN patch the historical cells in the Firebase console (admin bypasses the
   append-only rule the client obeys):
   - `leagues/braelinn/results/2026-09-15/finish/4/winnings`  20 → 0
   - `leagues/braelinn/results/2026-10-01/finish/4/winnings`  80 → 60

**Event 4 (15 Oct) did NOT add a third cell — but only by luck.** Guy, carrying
the $20, did not show, so no bounty was in play: `bounty: 0`, and
sum(winnings) = $580 = pot exactly. The scope is still the two cells above.

**The bug is live again for Event 5.** Matt T won on the 15th and now carries
the $20 into 22 Oct. If it is claimed before the code fix ships, Event 5 will
need a third cell patched. That is the deadline on this work: **22 Oct**.

## 6. Walk-ins create a second identity instead of tying to the roster (REAL)

Event 3's last-place row is literally `name: "Andy Kalina"`. The roster has
`{ name: "Andy", fullName: "Andy Jones" }` — seeded in Jacob's own original
upload (0c1bdd1, 19 Aug), and that short name has **never** appeared in a
result.

Season aggregation groups by the **short `name` on the result row**, and
`data.js` ~868 explicitly creates an entry for any name not on the roster
("Played but not on the roster in data.js — still counts"). So the standings
page currently lists both:

    Andy          0 events,   0 pts
    Andy Kalina   1 event,  300 pts

### RESOLVED 15 Oct — they are two different people

Jacob confirms Andy Jones and Andy Kalina are two men. Andy Jones stays on the
roster, unplayed. Andy Kalina was added as his own entry with short name
**exactly** `"Andy Kalina"` — matching the name Nate typed into the walk-in box
on 1 Oct — so his Event 3 result attaches to his roster entry with **no rewrite
of finalized history**. Verified against the real finish lists:

    Andy          events 0   rawPts   0
    Andy Kalina   events 1   rawPts 300   avgPlace 16

and every name in all three events' results now ties to a roster entry — no
orphans left.

Note for future merges: the grouping key is the short `name` on the stored
result row, NOT the roster's `fullName`. Editing `fullName` alone would never
have merged anything.

### The underlying flaw

The walk-in flow lets the host type a free-form name that becomes a new
identity. It should offer roster members first, or warn on a near-match, or
store a roster key alongside the display name. Otherwise every walk-in who is
already on the roster under a short name silently forks into two players.

This is why Shane Miner was added to the roster properly (short name "Shane")
rather than walked in as "Shane Miner" on the night.

## OPEN QUESTION — how many heads carry a bounty?

Jacob expects **Guy and Matt T both** to have $20 on them at Event 5. The app
does not work that way and never has:

- `BPL.bountyOn` returns ONE target — the most recent winner — at
  `$20 × consecutive wins`. "Somebody else winning resets it, whether or not
  the champion played that night."
- `LEAGUE.bounty.describe` says "$20 on **the last winner's** head".
- Live right now: `Matt T $20 (streak 1)`. Guy carries nothing.
- Event 4 confirms the absent-champion rule fired: Guy did not show, so
  `bounty: 0` was charged. Covered by a passing test,
  "A CHAMPION WHO DOESN'T TURN UP COSTS THE ROOM NOTHING".

So either Jacob's understanding is off, or the league rule is "an unclaimed
bounty persists until somebody actually collects it" — which the app has never
implemented. **Settle with Nate before Event 5.** It is $20 vs $40 off the top
of a real pot. If the rule really is multiple simultaneous bounties, that is a
schema change, not a tweak: `bounty`, `bountyOn` and `bountyWonBy` are all
scalars and would have to become lists.

# 22 Oct — the bounty rule, settled against the data

Jacob: *"the bounty was on Guy's head last week and he wasn't there, so it's on
his head tonight."* The app disagrees, and the full chain from the database is:

    2026-09-03  Tod wins       charged $0
    2026-09-15  Phil T wins    charged $20 on Tod,     taken by Sprayberry
    2026-10-01  Guy wins       charged $20 on Phil T,  taken by Jacob
    2026-10-15  Matt T wins    charged $0   <-- Guy carried it and did not show

Tonight `BPL.bountyOn(results, '2026-10-22')` returns **Matt T, $20, streak 1**.
Not Guy. Two divergences from Jacob's understanding:

1. **The head moved when Matt T won.** Guy's claim ended the moment somebody
   else took a night — "somebody else winning resets it."
2. **An unclaimed bounty does not roll forward.** The code comment says "their
   head keeps the price; it just isn't collected tonight", but that only holds
   while they are still the most recent winner.

And Matt T is not coming tonight, so `playing === false` and **$0 is charged.
The app will put a bounty on nobody.**

## Jacob's instinct is detecting a genuine hole

Under the current rule, **skipping a night is a free pass.** Guy won on 1 Oct,
carried $20, did not turn up on the 15th, Matt T won, and Guy now owes nothing
— he never had to defend it. That is a real design flaw, not a misunderstanding
of one. Whether the fix is "an unclaimed bounty persists until collected" is a
league decision, not a code decision. **Settle it with Nate.**

If the answer is that bounties persist, it is a schema change: `bounty`,
`bountyOn` and `bountyWonBy` are scalars and would have to become lists, since
two heads could be live at once (Guy's unpaid plus the current champion's).

## TONIGHT — keep it off the app

If $20 goes on Guy's head at the table but the app charges $0, the payout plan
is built on $20 more than is actually in the pot, and the last man paid comes
up short. That is worse than the bookkeeping bug.

**Run it as a side bet, outside the pot** — cash hand to hand, never entering
the app. The app's arithmetic stays correct and nothing is mislabelled.

(There is a hack — Nate could set a fixed kitty $20 higher via `setKittyAmount`
to pull the money out correctly — but the money flow would then call it
"season kitty", which is a lie in the permanent record. Not recommended.)

## Why tonight is the SAFEST night to ship the bounty fix

Because no bounty will be charged, every row has `bnty === 0`, so
`win + bnty === win`: the change to finalize is **provably a no-op for tonight's
record**. The risk we were avoiding on 15 Oct does not exist tonight.

The `data.js` half is not a no-op, though — season money becomes
`winnings + bounty`, so the two uncorrected rows read $20 HIGH the moment it
deploys. The console cells must land with the push, not after.
