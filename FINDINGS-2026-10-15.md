## 1. The bounty is counted twice in `winnings` (REAL, affects money display)

`game-state.js` ~line 1084, in `finalize()`:

```js
winnings: win + bnty,
bounty:   bnty,
```

The bounty is stored inside `winnings` **and** in its own `bounty` field, while
`pot` already has the bounty deducted off the top
(`pot = gross - kitty - bounty`). So whenever a bounty is claimed:

    sum(winnings) == pot + bounty

### Observed in live data

| Event | pot | sum(winnings) | delta |
|-------|------|------|-------|
| 1 — 2026-09-03 | $550 | $550 | ✓ (no bounty in play) |
| 2 — 2026-09-15 | $700 | $720 | +$20 |
| 3 — 2026-10-01 | $750 | $770 | +$20 |

**The cash at the table was correct both nights.** Jacob confirmed for Event 3:
Phil T handed him $20 on the knockout, and he collected $60 from the pot when he
busted in 5th. The record says `winnings: 80` — the $20 folded in on top of the
$20 already in `bounty`.

### The test agrees with the bug

`dress-rehearsal.js` ~line 365:

```js
if (handed !== game.pot + (game.bounty||0)) note(night,'money does not balance')
```

It *expects* the inflated sum. Correct data would make this check fail. That is
why nothing ever flagged it — code and test agree, and only the human-facing
results page disagrees ("Paid out $750" printed beside a column summing $770).

### Second-order damage: phantom cashes

`data.js` ~line 882:

```js
if (r.itm || (r.winnings || 0) > 0) p.cashes += 1;
```

Event 2: Sprayberry took the bounty off Tod but busted 5th when only four
places paid — `itm: false`, `winnings: 20` (all bounty). He is credited with a
cash he never made.

### Fix — CODE FIRST, THEN DATA. Order matters.

Season aggregation (`data.js` ~879) sums `winnings` and **never looks at
`bounty`**. So zeroing the data cells first would delete $40 of real bounty
money from the season record. Sequence:

1. `game-state.js`: `winnings: win` (drop `+ bnty`) — `winnings` means pool money.
2. `data.js` ~879: add bounty into the season money total, so bounties still count.
3. `data.js` ~882: key `cashes` off `itm` alone, not `winnings > 0`.
4. `dress-rehearsal.js` ~365: expect `handed !== game.pot`.
5. Full Playwright suite (24 browser files + 3 engine files).
6. THEN patch the historical cells in the Firebase console (admin bypasses the
   append-only rule the client obeys):
   - `leagues/braelinn/results/2026-09-15/finish/4/winnings`  20 → 0
   - `leagues/braelinn/results/2026-10-01/finish/4/winnings`  80 → 60
   - plus Event 4's equivalent if Guy's $20 gets claimed tonight

## 2. Event 3's high hand is a phantom (REAL, visible on standings)

Both Event 2 and Event 3 record `highHand` = Erik V, quads, "quad 10s, ace
kicker". Jacob confirms **he only did it once** — on 15 Sep.

`BPL.highHand(results)` derives the season record from every game's `highHand`
and lists everyone tied at the best category. Right now the standings page shows:

    Four of a kind — Erik V (2026-09-15) | Erik V (2026-10-01)

Same man, twice, for one hand.

### Root cause is the labelling, not the host

Jacob's original ask was *"master control should be able to input a new season
high"*. What shipped is per-night storage feeding a season-level derived record —
correct architecture, but:

- `game.html` ~306 comment calls the card **"The season high hand"**
- `data.js` ~646 calls `BPL.highHand` **"The best hand of the season"**
- but `renderHighHand()` labels it per-night: *"Nothing claimed tonight"*

So on 1 Oct the host entered the season's best hand into the night's slot. That
is a fair reading of a card whose own source comment says "season".

Worse, the input placeholder is a real hand somebody actually made —
`game.html` ~1432:

```js
window.prompt("Anything to add? (e.g. \"quad 10s, ace kicker\")", "")
```

An example should never be a real record. It invites exactly this.

### Fix

- **Data (safe to do any time, independent of §1):** delete
  `leagues/braelinn/results/2026-10-01/highHand` entirely. No high hand was
  recorded on 1 Oct — it should be absent, not corrected.
- **Code:** relabel the card "Tonight's best hand"; fix the misleading
  `game.html` comment; change the placeholder to a generic example; consider
  deduping `holders` so one person can't appear twice.
- **Tonight, no code needed:** tell Nate the card records *tonight's* best hand
  only — the season record builds itself.

## 6. Walk-ins create a second identity instead of tying to the roster (REAL)

Event 3's last-place row is literally `name: "Andy Kalina"`. The roster has
`{ name: "Andy", fullName: "Andy Jones" }` — seeded in Jacob's own original
upload (0c1bdd1, 19 Aug), and that short name has **never** appeared in a
result.

Season aggregation groups by the **short `name` on the result row**, and
`data.js` ~868 explicitly creates an entry for any name not on the roster
("Played but not on the roster in data.js — still counts"). So the standings
page currently lists both:

    Andy          0 events,   0 pts
    Andy Kalina   1 event,  300 pts

### RESOLVED 15 Oct — they are two different people

Jacob confirms Andy Jones and Andy Kalina are two men. Andy Jones stays on the
roster, unplayed. Andy Kalina was added as his own entry with short name
**exactly** `"Andy Kalina"` — matching the name Nate typed into the walk-in box
on 1 Oct — so his Event 3 result attaches to his roster entry with **no rewrite
of finalized history**. Verified against the real finish lists:

    Andy          events 0   rawPts   0
    Andy Kalina   events 1   rawPts 300   avgPlace 16

and every name in all three events' results now ties to a roster entry — no
orphans left.

Note for future merges: the grouping key is the short `name` on the stored
result row, NOT the roster's `fullName`. Editing `fullName` alone would never
have merged anything.

### The underlying flaw

The walk-in flow lets the host type a free-form name that becomes a new
identity. It should offer roster members first, or warn on a near-match, or
store a roster key alongside the display name. Otherwise every walk-in who is
already on the roster under a short name silently forks into two players.

This is why Shane Miner was added to the roster properly (short name "Shane")
rather than walked in as "Shane Miner" on the night.
